### Features

This library contains Services and Components for using PostgreSQL within the DataHub Framework.
It works as an adapter between DataHub and the [postgres](https://pub.dev/packages/postgres) dart library.

### Usage

Add `datahub_postgres` to the `dependencies` section of your projects
`pubspec.yaml` file, or simply run:

```shell
$ dart pub add datahub_postgres
```

### Migrations

The schema of a `@Data()` class changes over time, and an existing table does
not change with it. `PostgresqlMigrationService` closes that gap: it owns the
relations of the repositories declared inside it, and keeps them in step with
the model through a history of migration files that live in the repository
next to the code.

```dart
runApp([
  PostgresqlService(host: Config('postgres.host')),
  PostgresqlMigrationService(
    schema: [
      PostgresqlDataRepositoryService(bean: $Person.bean),
      PostgresqlRevisableRepositoryService(bean: $Article.bean),
    ],
  ),
]);
```

A migration is generated by comparing the data model against the schema the
existing migration files add up to - never against a live database, so it works
in CI and on a machine with nothing running:

```shell
$ datahub migrate plan
$ datahub migrate new add_person_email
```

The result is a plain `.sql` file under `resources/migrations`, reviewable in a
pull request and runnable with `psql`. Its leading comment carries the
structured description of the change, which is what the next `plan` replays:

```sql
/* datahub:migration
{
  "version": 2,
  "name": "add_person_email",
  "created": "2026-08-19T09:12:33.000Z",
  "destructive": false,
  "review": [],
  "changes": [ ... ]
}
*/

ALTER TABLE "public"."person" ADD COLUMN "email" varchar;
```

Two kinds of change are held back rather than applied blind. A migration that
can lose data needs `migration.allowDestructive`, and one that is only well
defined against an empty table - adding a `NOT NULL` column without a default,
for instance - is generated with a filled `review` list and refuses to run
until the statements have been edited and the list emptied.

At startup, `migration.mode` decides what happens:

```yaml
migration:
  mode: validate            # none | validate | apply
  directory: resources/migrations
  allowDestructive: false
```

`validate` is the default: the application refuses to start against a database
that is not at the head of the history, rather than failing later, one query at
a time. `apply` runs the pending migrations under an advisory lock, so ten
replicas starting at once still migrate exactly once. `none` leaves it to a
deploy step.

The remaining commands work against a database:

```shell
$ datahub migrate status     # what is applied and what is not
$ datahub migrate apply      # apply the pending migrations
$ datahub migrate verify     # report how the database differs from the history
$ datahub migrate baseline   # adopt a database that already has the schema
```

`baseline` is how an existing project moves over: it reads the schema that is
already there, writes it as the first migration and records it as applied.

A repository declared inside the migration service no longer creates its own
table. One declared outside it keeps creating it on startup, exactly as before.
